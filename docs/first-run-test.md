# どこでもデスク：GitHub取得から最初の動作を確かめる

2026-10-09作成、2026-10-10改訂。試験計画 v0.2。GitHub取得からの初回試用を踏まえ、[初回体験の設計](onboarding-design.md)の改訂と次の検証を整理する。改訂後の既存利用者による導入・専用チャット再開の試用レビューも確認済み。新規利用者・別環境の検証を次の対象とする。

## 今回の試験で知りたいこと

初めての利用者が自分のチャットに取得先を渡し、READMEを入口に総えもんと出会い、自分の仕事場と伴走役を作って、UIでその成果を見つけられるかを確かめる。

このチャットに蓄積した説明や、開発者が準備済みの作業フォルダがなくても、配布物だけで案内がつながるかを見る。途中で本人が何に迷ったか、質問が多すぎなかったかも残す。プログラムの起動成功と、人間が次の頼み方を理解できたことを別に記録する。

## 配布準備の現在地

MVPで検証した雛形v0.2を土台に、公開リポジトリへ生成器・雛形・案内をまとめた。取得先と現在の実装範囲は[README](../README.md)を参照する。リポジトリの取得確認と、以下の初回体験の試験は分ける。

生成・ブラウザ・ローカルGitへの保存と再クローンは[検証記録](../VALIDATION.md)にある。10月10日にmacOSのCodex・Astraで、GitHubからの取得、本人用の仕事場生成、伴走役・UI、専門担当の作成、同じ作業票の担当変更と更新を観測した。配布版の手順に合意フローが十分つながっておらず、担当を作ったことの紹介、専用チャットの提案、導入記録の最新化が改善点となった。

これは、既存のアカウント・認証・共通指示や利用履歴を持つ利用者が新しいプロジェクトで行った試用。AIが利用者の習熟度を把握できる可能性があり、完全な初対面・未経験者向けの試験とは扱わない。個人の業務内容・元対話・実チャットIDは配布物へ含めず、観測から得た改善点だけをここへ記す。

改訂案内による追試では、導入TASKと設定の分離、担当の紹介、専用チャットでの原本読み取り・訂正の継承・同じ作業票からの初回再開が成立したと報告されている。取得処理には既存コピーを使った復旧が含まれたため、既存の資料がない環境でのAIによる取得は別に確かめる。ここには試用者の業務内容やチャット情報を収録しない。

## OpenClawからの検証報告（2026-10-10）

Codex以外のAIエージェントが、macOS 15.7.3（Apple Silicon）・Python 3.9.6のOpenClaw環境で推奨フローを演習したとの報告を受けた。git clone、空の版の生成と表示名の反映、ポート8773でのHTML配信、unittest 14件、JavaScript構文確認が成功。目的記録・伴走役作成・名簿登録・導入TASKとonboarding.mdの接続・保存方式を後で決めるところまで、手順の演習もエラーなく一巡した。

ブラウザからのローカルURL閲覧は検証環境のポリシーで行えず、UIはHTTP応答まで。B3の描画・操作・目視と、B4の新規利用者本人による理解の確認は完了扱いにしない。対象コミットは報告に記載されていない。報告の出所・範囲は[検証記録](../VALIDATION.md)に残し、次の検証では対象版とともに未確認部分を記録する。

## 試験を始める前に用意するもの

1. **試験用の配布先と版。** 公開リポジトリの実際のURLと、固定したタグまたはコミットを記録する。
2. **配布する中身。** 導入用README、総えもんとUI担当の役割、空の雛形、必要な手順、生成器、UI、保存・再開ガイド。研究用の原資料、実業務・私的な対話・接続設定を配布物へ混ぜない。練習例は本人の仕事場に入り込まないよう区別する。
3. **合意フローへの接続。** READMEから、自己紹介、PCの保存先、動機・伴走役、導入TASK・UI確認へ進めることを確かめる。口調・キャラクター・名前の質問を必須にせず、既知の情報は使う。プラグインは不要。
4. **導入作業の記録。** チャットで最初の進捗を示し、保存先が決まったら導入TASKへ移す。UIがその原本を読み取れるようにする。onboarding.mdとの二重の状態管理を避ける。
5. **新しい試験環境。** 開発者の作業フォルダや過去の対話を与えず、新しい会話と空の作業場所から始める。ホスト共通の指示・有効プラグイン等がある場合は記録し、完全に初期状態の環境とは呼ばない。

これらは改訂した初回体験の再試験に向けた準備条件。公開版の取得確認と、その版による利用者試験は分ける。実装と配布時には、実際の配布対象を選び、送信先と対象の確認手順に従う。

## 最初に渡す依頼文

実在するURLと版を入れて、新しい試験チャットへ渡す。段階ごとの正解やこの設計書を先回りして与えず、READMEから案内できるかを見る。

> このチャットで「どこでもデスク」を使ってみたいです。指定のGitHubリポジトリの試験版を取得し、READMEを読んで、初めての利用者として案内してください。まずこのパソコンに仕事場を作って、最初の画面を確認するところまでお願いします。GitHubへの私の仕事の保存は後で決めます。
>
> 取得先：実際の試験用リポジトリURL
> 対象版：固定したタグまたはコミット

公開版の取得と、本人の仕事場を保存するためのGitHub同期を区別する。利用者用リポジトリの作成やpushは、この最初の依頼に含めない。

## 最初の試験範囲

| 段階 | 行うこと | 観測と判定 |
|---|---|---|
| A1 取得 | 新しい場所へ対象版を取得する | URL・版・取得先が一致し、既存の仕事場を上書きしない。取得不能なら理由と再開位置が分かる |
| A2 総えもん登場 | READMEから必要な手順と役割を読む | 自己紹介と仕組みの説明が始まる。利用者が「総えもん用の長いプロンプト」を別途探さなくてよい |
| A3 必要な準備 | PCの保存先と必要な実行能力を確認する。好みは必要時だけ扱う | 口調・キャラクターを一律に聞かず、未指定で進められる。地域や習熟度を決めつけない |
| B1 目的と名前 | 本人の発言から目的を整理し、表示名と新しい保存フォルダを用意する。名前は仮でもよい | 既知のことを聞き直さず、本人の発言とAIの解釈を区別する。配布元を取り違えない |
| B2 最初の相棒 | 動機の伴走役を作って名簿へ登録する | 総えもん・UI担当・伴走役の3担当が対応する。架空例や同名担当を重複登録しない |
| B3 UIを確認 | UI担当が既存の画面を整え、表示を確認する | 担当一覧と「仕事場を準備する」のTASK、最新の成果・次の一手が一致する。onboarding.mdは設定とその原本への入口で、進捗を二重管理しない |
| B4 一巡を終了 | 総えもんが担当・成果・保存場所・続きの頼み方を伝える | 本人の反応から理解を確かめ、未確認なら未確認とする。GitHub同期・別チャット・定期起動の未設定を混同しない |

**最初の試験依頼はA1〜B4までにする。** 仕事場づくり自体を最初の仕事として扱う。業務の完了はこの試験の合格条件に含めない。試験中に本人が追加の業務を依頼した場合は、導入の区切り・未確認事項を記録してから進み、追加依頼以後を別の観測として扱う。

UIの画面が開いた時点と、本人が内容を確認できた時点を区別する。自動で開けない場合は、確認済みの起動方法とURLを案内し、その経路で表示できたかを記録する。成功したような表示だけでは完了にしない。

## 試験中に記録すること

取得元と版、利用したAI・実行環境、生成先、通過した段階、成果原本、本人の反応、つまずいた場所、追加で必要だった説明、次の一手を残す。所要時間や質問数は改善の手掛かりにし、最初から固定の合否基準にしない。

開発者が途中で教えた場合は、その内容と教える前に止まった場所を記録する。助言後に進んだ結果を、配布物だけで導入できた結果とは分ける。問題を直したら版を変え、新しい空の場所から再試験する。

本人の確認は短く、次の三点を見る。会話や反応から分かることは使い、三問を一律に出す試験にはしない。

- 仕事場と成果がどこにあるか分かったか。
- 総えもん・伴走役・UI担当が何をしてくれるか分かったか。
- 次に担当を増やしたい、続きをしたいとき、何と頼めばよいか分かったか。

## その後に分けて行う試験

1. **担当追加と引き継ぎ。** 担当・名簿・原本を作り、紹介と同じチャットでの兼務が伝わるか。継続業務には理由を添えて専用チャットを勧め、同じチャットで続ける希望も尊重するか。選んだ場合はAIが開始文と原本を用意し、新しいチャットで目的・訂正・成果・未完了事項を説明し直さず再開できるか。準備・作成や送信・実際の読み取りと着手を分ける。単発の依頼では不必要なチャットを増やさないか。
2. **途中からの再開。** 導入の途中と完了後の両方を試し、同じ質問・役割作成・成果物作成を重複しないかを見る。
3. **保存と別端末。** 本人の非公開リポジトリへの保存、再取得、環境ごとの設定を試す。配布元の取得試験と混ぜない。
4. **利用者の経験と設定。** 既存環境を使う経験者と、PCでAIを使えるがGitに詳しくない新規利用者を分ける。口調・名前を指定する場合／しない場合、急ぐ場合／自分で学びたい場合を試し、質問省略と必要な案内が両立するかを見る。利用可能な共通指示・記憶・認証の条件を記録する。
5. **PCのAI環境。** Antigravity・Hermes等でREADMEから始め、生成・Python実行・UI表示・役割読取・作業記録・次の会話からの再開を個別に確認する。未試験の環境を対応確認済みと表示しない。
6. **将来の遠隔利用とプラグイン。** 準備済みの仕事場を遠隔で読み書き・保存・再開できるかと、任意のプラグインから同じ案内へ進めるかを別工程で試す。現行の本体利用の合格条件には含めない。

本体の試用で見つかった負担を先に直す。プラグインを作る場合も、GitHubのREADMEから始める体験と役割・仕事の原本を共通にする。
